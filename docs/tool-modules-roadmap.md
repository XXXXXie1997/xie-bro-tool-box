# 蟹小箱 · 工具模块优化与扩展路线图

**定位前提（按你的决定）**：纯工具产品，**不接入远程控制**，不做工单/派单/结算等服务平台功能。
本文只回答一件事：**这 9 个工具接下来该怎么优化、该加哪些工具。**

调研基础：[电脑服务聚合平台调研](service-platform-research.md)（含联想官方价目表、品类优先级、合规红线）。那份报告里关于服务履约、远程协助、EDI、结算的章节**按你的定位已不适用**，保留作为市场背景。

---

## 0. 先回答一个绕不开的问题：工具的「付费理由」是什么

不做服务层，就必须直面一个事实（调研 1.3.1 节）：

> **微软电脑管家、火绒、360、腾讯电脑管家、Dism++ 全部免费，而且能力比你全。**
> 「清理得更干净」不构成付费理由。

所以蟹小箱的付费理由只能从下面三条里选，**而选哪条会直接改变优化方向**：

| 定位 | 谁付钱 | 优化重点 | 风险 |
| --- | --- | --- | --- |
| **A. 工程师的作业工具** | 维修店／同行／你自己 | 效率、批量、留痕、报告、可解释 | 受众小，但付费意愿明确（一个工程师省 20 分钟/单就是钱） |
| **B. 终端客户自助工具** | 普通用户 | 极简、可信、报告、安全感 | **必须解决「凭什么不用免费的 360」**，很难 |
| **C. 免费引流工具** | 不直接收钱 | 传播性、报告分享、品牌 | 需要后端变现，而你说不做服务层 → 闭环断裂 |

**我的建议：以 A 为主，兼顾 B。**
理由：你现在这套代码的**独特优势恰好是 A 需要的**——严谨的安全删除机制、可解释的清理后果、逐项确认、不申请提权。这些在 B 场景里是「啰嗦」，在 A 场景里是「专业」。而且 A 场景下你能收钱（卖给同行），B 场景下你很难收钱。

**如果确实是 B（直接卖终端客户）**，那第 3.1 节（报告）和第 3.5 节（客户模式）的优先级要再提高一档，同时要补「首次体验」和「信任建设」两件事。

## 1. 现状盘点：9 个模块的能力边界

| 模块 | 能做什么 | 明确的边界（来自各自 README／代码） | 成熟度 |
| --- | --- | --- | --- |
| **垃圾清理** | 6 类：过期临时文件、崩溃转储、错误报告、图形着色器缓存、8 款浏览器缓存、回收站 | 只扫当前用户目录（`CleanerPaths` 只有 Local/Roaming）；不碰桌面/下载/文档/聊天记录/网盘；不申请提权 | ★★★★★ |
| **文件扫描** | 大文件（阈值 ≥50MB）、格式筛选、重复文件内容校验 | **只读，不删除**；最多检查 500,000 项 | ★★★★ |
| **启动项管理** | 当前用户 Run 关闭/恢复、启动文件夹；所有用户 Run 只读 | 不处理 RunOnce／服务／驱动／计划任务／商店应用 | ★★★ |
| **内存释放** | 物理内存展示、按需整理后台进程工作集 | 不结束进程、不空待机列表、不提权 | ★★★ |
| **磁盘空间分析** | 目录排行、占比、逐层查看、打开位置 | **只读，无删除、无「可清理」判断**；最多 200,000 项 | ★★★★ |
| **软件卸载** | HKCU/HKLM 32/64 位卸载信息、搜索、调用原卸载程序 | **不扫描残留**；商店应用走系统设置 | ★★★ |
| **批量重命名** | 前缀、文字替换、序号、预览、撤销 | 不递归子目录、无大小写单独变更、无文件名交换 | ★★★★ |
| **文件整理** | 按扩展名归类、预览、冲突保护、撤销 | 只处理当前层普通文件 | ★★★★ |
| **网络诊断** | 适配器/地址/网关/DNS/HTTPS 检查、清空 DNS 缓存、**导出报告** | 只读诊断，不自动重置网络 | ★★★★ |

**一句话总结**：功能覆盖不错，**但整体是一个「九个独立小工具」的状态，而不是「一个产品」**。

## 2. 四个结构性缺口（决定优化优先级）

### 缺口一：没有统一的「交付物」★★★

现在所有模块跑完，结果只停留在界面上——关掉页签就没了，客户看不到，工程师也留不下证据。

> **唯一的例外是上网排查**：`tools/network-diagnostics/src/NetworkDiagnostics.cs` 已经实现了一套完整的报告导出——`BuildReport()`（第 115 行）、`CanExport`（第 109 行）、`SaveFileDialog` + UTF-8 BOM 写文件（第 163–172 行），连隐私提示都写好了（「含网络地址和设备名称，请仅发给信任的人」「报告仅包含本次检查，不包含密码和浏览历史」）。

**这套东西已经跑通了，只是没有被提取成公共能力。** 这是本次路线图里**投入产出比最高的一件事**。

### 缺口二：没有跨模块编排，就没有「一次体检」★★★

现在工程师要判断「这台电脑什么问题」，得逐个打开 9 个模块各点一次扫描。工具的**门面**应该是：

> 点一次「开始体检」→ 8 个只读扫描并行跑完 → 汇总成一张表：
> 「C 盘可用 2.1 GB（危险）｜发现 47 GB 可回收｜启动项 14 个可关闭｜内存占用 87%｜网络正常｜3 个软件有残留」

这既是首次体验的门面，也是最好的销售工具（发现的问题就是下一步要卖的服务）。

### 缺口三：能力被 `asInvoker` 限制——这是「清不出空间」的根本原因 ★★

[app.manifest](app.manifest#L4) 写的是 `requestedExecutionLevel level="asInvoker"`。这是一个**正确的安全选择**，但代价是：

**空间占用的大头你一个都碰不到。**

| 空间大头 | 典型大小 | 需要提权 |
| --- | --- | --- |
| WinSxS 组件存储（DISM 清理） | 3–10 GB | ✅ 需要 |
| Windows 更新缓存 | 2–8 GB | ✅ 需要 |
| `hiberfil.sys` 休眠文件 | ≈ 内存大小（8–32 GB） | ✅ 需要 |
| `Windows.old` | 5–20 GB | ✅ 需要 |
| 系统还原点 | 数 GB–数十 GB | ✅ 需要 |
| 页面文件 `pagefile.sys` | 4–16 GB | 迁移需提权 |

**这就是为什么「跑完清理只回收了几百 MB」——用户感知最强烈的「C 盘红了」问题，恰恰在你现在够不到的地方。**

这不是说要改成常驻管理员（那是错误方向），而是应该提供**按需提权**（见 3.4）。

### 缺口四：没有「发现问题 → 处理问题」的闭环 ★★

磁盘分析告诉你 `C:\Users\xx\AppData\Local\Temp` 有 8 GB，但你不能一键去清它；垃圾清理说「有 47 GB 可回收」，但工程师想看看这些空间到底在哪。**模块之间是孤岛。**

## 3. 横切优化（影响全部模块，优先级最高）

### 3.1 ★★★ 统一报告与导出能力（提取现有实现）

- **做什么**：把 `network-diagnostics` 里已经跑通的报告模式提升为 `Platform.UI` 的公共能力，让每个模块都能产出统一格式的报告并导出。
  - 新增 `Platform.UI/IReportable.cs`：定义 `BuildReport()`、`CanExport`、`ReportTitle`。
  - 新增 `Platform.UI/ReportExporter.cs`：统一处理 `SaveFileDialog`、文件名（`蟹小箱-{模块名}-{yyyyMMdd-HHmmss}.txt`）、**UTF-8 BOM 编码**（现有实现已经是对的，中文 Windows 记事本必须带 BOM）、异常处理（IOException／UnauthorizedAccessException）。
  - 新增 `Platform.UI/ReportBuilder.cs`：提供统一的报告头（产品名、时间、版本、系统版本、机器画像）和分段拼装。
  - 所有 9 个模块的 `Model` 实现 `IReportable`，`FooterActions` 加导出按钮。
- **报告内容规范**（统一骨架）：
  ```
  蟹小箱 · {模块名}报告
  生成时间 / 版本 / 系统 / 机器画像（机型、内存、C 盘容量与可用）
  ── 结论 ──
  一句话结论 + 影响说明 + 建议操作
  ── 明细 ──
  各项结果
  ── 说明 ──
  本次检查范围 / 未检查的内容 / 隐私声明
  ```
- **额外建议**：给垃圾清理和体检报告加**图片导出**（PNG 长图）。文本报告适合发给技术人员，**图片报告适合发给不懂电脑的人看**——这是两个不同的受众。
- **为什么优先**：① 已有跑通的实现可抄，风险低；② 它是把「9 个工具」变成「1 个产品」的唯一办法；③ 它同时解决了付费服务的凭证问题（如果以后要做服务，这一步不用返工）。
- **验收**：任意模块跑完后都能导出一份带时间戳、可在记事本正常打开的中文报告。

### 3.2 ★★★ 一键体检编排引擎

- **做什么**：新增一个编排层，串行或并行调用现有模块的**只读扫描**入口，汇总成一张体检表。
  - 落点：新增 `Services/HealthCheck.cs`（平台层），或做成一等模块 `system-report`。
  - **关键设计**：编排层**只调用各模块已有的只读扫描，不执行任何破坏性操作**。现有 9 个模块的扫描都是安全的（垃圾清理扫描、文件扫描、磁盘分析、启动项读取、软件清单、网络检查都是只读），可以放心编排。
  - 内存释放的「整理」是写操作，**不纳入体检**，只读内存状态。
- **体检表内容建议**：
  | 检查项 | 数据来源（现有模块） |
  | --- | --- |
  | C 盘／各盘容量与可用空间、健康度分级 | 磁盘空间分析 + 驱动器信息 |
  | 可回收空间分类汇总 | 垃圾清理（只扫描，不清理） |
  | Top 大文件与重复文件占用 | 文件扫描（只读） |
  | 启动项数量与可关闭项 | 启动项管理（只读） |
  | 内存总量／占用／可整理量 | 内存释放（只读） |
  | 已安装软件数量与体积排行 | 软件卸载（只读） |
  | 网络连通性 | 网络诊断（只读，可跳过以避免联网） |
  | **系统级空间占用（需提权项）** | 🆕 见 3.4 |
- **为什么优先**：这是工具的门面，也是「一屏看懂这台电脑」的唯一办法。**没有它，9 个模块永远只是 9 个小工具。**

### 3.3 ★★ 结果 → 处理的闭环跳转

- **做什么**：体检表和磁盘分析的结果里，每一项可清理项旁边加「去处理」按钮，点击后切换到对应模块页签并**预填参数**（例如：跳到垃圾清理并自动开始扫描、跳到文件扫描并预填该目录）。
- **技术落点**：`Views/MainWindow.Tabs.cs` 已有 `OpenModule(ModuleDefinition)` 的页签机制（第 30 行附近），需要扩展为可传参；各模块 `Create(IPlatformContext)` 工厂方法需要一个可选的初始参数。
- **为什么**：把「发现问题」和「解决问题」连起来的距离，直接决定工具好不好用。

### 3.4 ★★ 按需提权（解锁系统级清理）

- **现状**：`asInvoker`，全部模块只能处理当前用户范围。
- **不建议**的做法：把主程序改成 `requireAdministrator` 常驻管理员——会带来 UAC 每次弹窗、拖拽失效、安全面扩大等问题，且违背现有「默认普通用户权限」的既定决策。
- **建议做法**：**按需提权 + 显式同意**。
  - 主程序保持 `asInvoker`。
  - 涉及系统级操作的模块（垃圾清理的系统类目、C 盘瘦身）在用户**明确点击**「以管理员身份处理」后，用 `runas` 动词重启自身或启动一个**独立的小 helper 进程**（只做系统级清理，不做界面）。
  - 好处：普通使用零打扰；需要时一次 UAC；helper 程序攻击面极小。
- **技术注意点**（提权后容易踩的坑）：
  1. **单实例互斥量**：`Services/DesktopInstance.cs` 用命名互斥量防重复实例，提权重启后要确保不会把提权实例误判为「第二个实例」而激活旧窗口。
  2. **托盘图标**：提权进程不能与普通进程共享托盘图标，helper 方案（无界面）可以规避这个问题。
  3. **DPAPI 与数据目录**：DPAPI 是按用户加密的，**同一用户提权后仍可解密**（这一点没问题），但要确认 helper 用的是同一用户而非 SYSTEM。
  4. **设置读取**：helper 需要读取平台的模块设置（如排除目录），要确保路径解析一致。
- **解锁的能力**（按价值排序）：
  | 能力 | 实现方式 | 典型回收 |
  | --- | --- | --- |
  | Windows 更新缓存 | 清理 `C:\Windows\SoftwareDistribution\Download` | 2–8 GB |
  | WinSxS 组件清理 | `DISM /Online /Cleanup-Image /StartComponentCleanup` | 3–10 GB |
  | `Windows.old` | `cleanmgr` 或受控删除 | 5–20 GB |
  | 休眠文件 | `powercfg /h off`（**必须明确告知会关闭休眠**） | ≈ 内存大小 |
  | 旧的系统还原点 | 保留最新一个，删除其余 | 数 GB |
- **安全要求**：系统级操作必须**比现在的用户级操作更保守**——每项单独确认、说明后果、执行前创建还原点（见 `protection` 模块）。现有 `SafeFile` 的句柄校验机制应原样复用到系统级路径。

### 3.5 ★★ 客户模式 / 工程师模式

- **做什么**：一个开关（或启动参数）切换界面复杂度。
  - **工程师模式**：现在的完整界面——分类、逐文件明细、半选、排除目录、技术报告。
  - **客户模式**：一句话 + 一个大按钮 + 进度 + 结果 + 图片报告。不显示路径、不显示技术术语。
- **为什么**：即使不做远程服务，这两个受众也真实存在——同行要效率，普通用户要「别让我做决定」。
- **落点**：`platformsettings.json` 加一个 `uiMode` 字段；`Views/MainWindow.xaml.cs` 根据它决定加载哪些视图。

### 3.6 ★ 任务队列与批量执行

- **做什么**：允许把多个操作排成队列依次执行（体检 → 清理 → 报告），而不是一个个点。
- **为什么**：工程师场景下省时间；普通用户场景下「一次搞定」。
- **注意**：现有多数模块是「一次一个任务」的模型（`ToolModel.Run` 有 `if (IsBusy) return;` 的保护），做队列需要先做任务抽象。**建议排在 3.1–3.5 之后**，不要一开始就做。

## 4. 现有 9 个模块的具体优化清单

### 4.1 垃圾清理 ★★★★★ → 优先扩展

**现状**：6 个类目、13 条内部规则，安全机制行业领先（句柄校验 + 卷/文件 ID/硬链接数核对）。

**可加的用户级类目（不需要提权，可直接做）**：
| 类目 | 路径 | 说明 |
| --- | --- | --- |
| 缩略图与图标缓存 | `%LocalAppData%\Microsoft\Windows\Explorer\thumbcache_*.db`、`iconcache_*.db` | 需处理「资源管理器占用」，建议提示后跳过 |
| 字体缓存 | `%LocalAppData%\FontCache` | 小但安全 |
| 传递优化缓存 | `%SystemRoot%\SoftwareDistribution\DeliveryOptimization` | 部分需提权，可只做用户部分 |
| 应用缓存（非浏览器） | 网易云音乐、Steam、抖音 PC、WPS、钉钉、企业微信等的标准缓存目录 | **需要逐款核实**，按现有浏览器适配的严谨度做 |
| 已卸载程序的残留目录 | `%LocalAppData%` 下无对应安装项的目录 | 风险高，建议只「列出并提示」不自动清理 |

**建议谨慎处理、只展示不删除的**：
- **微信／QQ 文件缓存**——这是 C 盘占用的大头之一（几十 GB 很常见），但现有边界明确「不碰聊天记录」。**正确做法是「展示占用大小 + 引导用户用微信自带的『存储空间管理』清理」**，而不是替用户删。这既解决了用户痛点，又不越界。
- **OneDrive／云盘占位文件**——只展示占用。

**需要提权的系统级类目**（见 3.4）：Windows 更新缓存、WinSxS、`Windows.old`、休眠文件、系统还原点。

**其他优化**：
- **清理前自动创建还原点**（可选开关，默认对系统级操作开启）。
- **报告导出**（3.1）。
- **「上次清理至今」**：读取 `last-result.json` 展示上次清理时间与回收量，给用户正反馈。

### 4.2 磁盘空间分析 ★★★★ → 加「可清理性」标注

**现状**：只读、目录排行、逐层查看。明确**不判断可清理**（这是安全的设计）。

**建议优化**：
- **标注「可清理」目录**：把垃圾清理的规则路径与磁盘分析结果关联，在目录列表里标出「此目录有 8 GB 可被垃圾清理回收 → 去处理」。**这不改变「不自动判断」的原则**——它是引用已有规则，不是猜测。
- **区分逻辑大小与实际占用**：README 已承认「硬链接按路径计入，不等于物理磁盘占用」。补上稀疏/压缩文件的实际占用（garbage-cleaner todoList 第 71 行已列此需求）。
- **与文件扫描（大文件/重复文件）联动**：在目录上直接显示「大文件 N 个」「重复文件可释放 X GB」。
- **Top N 快照对比**：保存一次分析结果，下次对比「这个目录长了 5 GB」——这比单次分析有用得多。

### 4.3 软件卸载 ★★★ → 加残留扫描

**现状**：清单 + 调用原卸载程序。`todoList.md` 里已把「残留处理」列为「后续评估」。

**建议优化**（这也是一个高价值的独立卖点）：
- **卸载残留扫描**：扫描注册表（`HKLM/HKCU\Software` 下无对应安装项的项）、安装目录残留、开始菜单快捷方式、启动项残留、计划任务残留。**只列清单，逐项确认删除**（沿用现有的谨慎风格）。
- **按占用空间排序**：现在只能按名称搜索，用户最想知道的是「哪个软件占地方」。
- **批量卸载**：一次选多个，依次调用卸载程序。
- **卸载前创建还原点**。
- **图标显示**：现在是纯文本列表，加应用图标能显著提升观感。

### 4.4 启动项管理 ★★★ → 扩范围 + 加影响评估

**现状**：当前用户 Run 可关可恢复；所有用户 Run 只读；启动文件夹。不碰 RunOnce/服务/驱动/计划任务。

**建议优化**：
- **加计划任务**（`Tasks` 下非微软任务）：这是现代软件自启动的主要方式，不做就等于漏了一半。需按白名单方式谨慎识别。
- **加非微软服务**（`Win32_Service` 中非 Microsoft 签名的自动启动服务）：风险较高，**建议只读展示 + 跳转系统「服务」界面**。
- **启动耗时影响评估**：Windows 自己在「任务管理器 → 启动」里有「启动影响」数据（可读注册表 `StartupApproved` 及 Explorer 的启动项枚举）。展示「高影响」项，用户才知道该关哪个。
- **一键优化建议**：给出「建议关闭」列表并支持批量操作。

### 4.5 内存释放 ★★★ → 加进程排行

**现状**：物理内存展示 + 按需整理后台进程工作集。如实展示前后差值（这点做得很好）。

**建议优化**：
- **进程占用排行**：列出 Top 20 内存占用进程，标注「可安全关闭」的建议（浏览器标签页过多、后台常驻软件）。
- **诚实定位**：README 已明确「可用内存增多不等于运行速度提高」，这个诚实态度要保持。可以考虑把「整理工作集」降级，把「找出谁在吃内存」升级为主功能——**后者才是用户真正想知道的**。

### 4.6 网络诊断 ★★★★ → 从诊断扩展到「按需修复」

**现状**：只读诊断 + 清空 DNS 缓存 + 导出报告 + 系统设置跳转。

**建议优化**（todoList 里已有「按需执行修复」）：
- **按需修复项**（每项单独确认 + 说明后果）：
  | 修复项 | 命令／方式 | 风险 |
  | --- | --- | --- |
  | 清空 DNS 缓存 | ✅ 已有 | 无 |
  | 重置 Winsock | `netsh winsock reset`（**需重启**） | 中，会重置 LSP |
  | 重置 TCP/IP | `netsh int ip reset` | 中 |
  | 重置代理设置 | 清除 WinHTTP/WinINET 代理 | 低（公司代理环境需提示） |
  | 释放／续租 IP | `ipconfig /release` + `/renew` | 低 |
  | 重置 hosts 文件 | 恢复默认 | 中（可能删掉用户自建条目，先备份） |
- **联网环境的额外价值**：这是「C 盘满了」之外第二高频的求助场景，标准化程度高，值得投入。
- **报告升级**：现有 `BuildReport()` 改为实现统一的 `IReportable`（3.1）。

### 4.7 文件扫描 ★★★★ → 加工信与安全建议

**现状**：大文件、格式筛选、重复文件（内容校验）。**明确不提供删除**（安全设计）。

**建议优化**：
- **重复文件分组展示**：现在按大小/内容分组，但用户最需要的是「这一组里保留哪个、删哪个」的**建议**。可以标注「保留修改时间最新／路径最短的」，**但删除仍需用户自己去资源管理器操作**（保持零删除风险）。
- **大文件按位置分组**：把「下载目录 32 GB」这种聚合结论摆在最前面，比一长串文件列表有用。
- **与磁盘分析联动**：见 4.2。

### 4.8 / 4.9 文件整理、批量重命名 → 低优先级

这两个模块完成度已经很高，且**与「C 盘/性能」主线关系较弱**。建议：
- 补 `批量重命名` 的「递归子目录」和「扩展名变更」（最常见的两个诉求）。
- 其他暂不投入。

## 5. 建议新增的模块（按 ROI 排序）

| 优先级 | 模块 ID | 功能 | 复用现有代码 | 需提权 | 难度 |
| --- | --- | --- | --- | --- | --- |
| ★★★ | `protection` | **系统还原点与备份引导**：创建/查看/删除还原点，服务前安全网 | 新增，调 `SystemRestore` WMI 或 `Checkpoint-Computer` | ✅ | 低 |
| ★★★ | `system-report` | **系统体检与报告**（即 3.2 编排引擎的模块化形态） | 调用全部现有只读扫描 + 3.1 报告 | 部分 | 中 |
| ★★★ | `disk-relief` | **C 盘瘦身与搬家**：系统级空间清理 + 用户目录重定向 + 软件跨盘搬家（junction） | 复用 `SafeFile` 句柄校验 + 磁盘分析 | ✅ | **高** |
| ★★☆ | `cleanup-adware` | **弹窗广告与流氓软件清理**：计划任务、启动项、浏览器快捷方式劫持、hosts、代理劫持 | 复用启动项管理 + 网络诊断 | 部分 | 中 |
| ★★☆ | `runtimes` | **运行库与游戏环境修复**：VC++／DirectX／.NET 检测与安装、常见游戏环境错误 | 新增；需联网下载（可让用户自备安装包） | 部分 | 中 |
| ★★☆ | `crash-doctor` | **蓝屏与崩溃溯源**：读 minidump／事件日志，解析 bug check code，输出可解释结论 | 复用垃圾清理的 `CrashDumps` 扫描 + 报告 | ❌ | 中 |
| ★☆☆ | `driver-doctor` | **驱动检测**：枚举设备与驱动版本，标注异常设备，跳转厂商下载页 | 新增 | 部分 | 中 |
| ★☆☆ | `printer-share` | **打印机与共享修复**：打印后台服务、共享权限、驱动重装 | 新增 | ✅ | 中 |
| ★☆☆ | `update-doctor` | **Windows 更新修复**：更新卡住／失败的常见修复 | 新增 | ✅ | 中 |
| ★☆☆ | `newpc-setup` | **新机开荒**：常用软件清单与静默安装（**仅正版/免费，客户自备介质**） | 新增 | ✅ | 中 |

**三个最该先做的说明：**

- **`protection`（还原点）** —— 它本身不产生「成绩」，但它是**所有高风险操作的前置条件**。有了它，你才敢做 `disk-relief` 和系统级清理。**这是风险最低、收益最长远的一个。**
- **`system-report`** —— 前面 3.2 已经论证过。它也可以不做成独立模块，而是作为平台层的「体检」页签，两者都行。
- **`disk-relief`** —— **这是真正解决「C 盘红了」的模块**，也是你目前唯一够不到的大空间。难度高（junction／重定向有数据风险），但它是整个产品最有价值的一块。建议**先做只读的「空间去哪了 + 能回收多少」分析版本**，验证价值后再做实际搬运。

> ⚠️ **`newpc-setup` 的红线提醒**：只能安装正版或免费软件，且**必须由客户自备安装介质**。调研发现联想官方的应用指导 SKU 明确要求「需自备安装介质」，其年卡细则也白纸黑字写「不含行业专用软件、破解软件」——**连联想都不敢碰这条线**。详见调研报告 4.3 节。

## 6. 三批实施建议

### 批次一（建议 2–4 周）——把工具变成一个产品
1. **统一报告与导出**（3.1）——提取 `network-diagnostics` 的现成实现，9 个模块全接入 ★★★
2. **一键体检**（3.2）——只读编排，汇总成一张表 ★★★

## 7. 三个需要你决定的问题

1. **工具给谁用——工程师、终端客户，还是两者？**（第 0 节）
   决定 `客户模式` 和 `报告图片导出` 的优先级。**建议两者兼顾，工程师模式为主。**

2. **要不要做按需提权？**（3.4）
   这是「能不能真正解决 C 盘红了」的分水岭。
   不做 → 永远只能回收几百 MB，工具价值有限；
   做 → 需要额外处理单实例、托盘、helper 进程，但能回收 **10–40 GB**。
   **建议做，但先做 `protection` 还原点。**

3. **要不要代码签名？**
   与工具功能无关，但直接决定分发转化——客户双击时看到「未知发布者」的 SmartScreen 警告，会直接流失。
   调研发现行业普遍用免费工具，**你的工具本身没问题，问题在于「敢不敢双击」**。
